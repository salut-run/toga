This file is the persistent coordination state for the experimental `toga-winui3` backend. Future agents MUST read this file before planning or editing WinUI 3 backend work, MUST update it whenever new status, blockers, test results, or next tasks are discovered, and MUST update it again before giving a final response so context survives compaction and handoff.

## Current Status

- Last updated: 2026-05-28.
- Active Toga branch: `winui3-backend`.
- Active slice: Physical WinUI menu keyboard accelerator coverage has been added after WinUI startup resource debug noise, native Windows notification-area status icons, WinUI startup document/file activation, WinUI document file-drop opening, native WinUI window-management menu actions, Win2D Canvas visual-reference coverage, WebView2-backed MapView rendering, native toolbar, menu probing, app icon updates, about dialogs, native WinUI message dialogs and Windows App SDK file/folder pickers, document save-as routing, focused window lifecycle behavior, app exit/cursor/current-window cleanup, focused app presentation behavior, full desktop app suite stabilization, native command shortcut conversion/display, screen metadata/image capture, window image capture, Table/Tree select-all keyboard shortcuts, cell icons, and cell widgets, Table keyboard boundary shortcuts, WinUI custom font registration, OptionContainer content-based rehinting and tab icons, TimeInput backend-enforced limits, Selection/NumberInput/PasswordInput text alignment, and the full window suite were completed; remaining work focuses on true native fullscreen/presentation parity, WinUI-specific DPI coverage, native dialog/picker hardening, OS-level status-icon interaction coverage, and provider/offline hardening for MapView.
- Branch lineage: this branch builds on Oliver's WinUI 3 proof-of-concept seed commit `595679a2a` and the local scaffolding commit `02d039f25 Add experimental WinUI 3 backend scaffolding`.
- Related Salut state: stable Windows support lives on Salut branch `fix/windows-support-revival`; Salut WinUI experimentation lives on `experiment/winui3-backend`.
- The latest completed WinUI slice builds out Image, ImageView, Button, Label, TextInput, MultilineTextInput, DateInput, TimeInput, OptionContainer, Slider, SplitContainer, Switch, Selection, Divider, NumberInput, PasswordInput, ProgressBar, ScrollContainer, ActivityIndicator, Table, WebView, font handling, staging measurement, color probes, and backend probes.
- WebView was initially believed to require a Core WebView2 HWND controller bridge, but after the Briefcase dev environment was refreshed the installed `win32more.Microsoft.UI.Xaml.Controls` package exposed the XAML `WebView2` control. The backend now uses that native control directly.
- MultilineTextInput cannot inherit TextInput focus tracking directly because the core `MultilineTextInput` interface does not expose `on_gain_focus`/`on_lose_focus`; its backend must use native focus without dispatching TextInput-only focus handlers.
- Image support currently uses a PNG-backed `NativeImage` wrapper around WinUI `BitmapImage`; broader JPEG/GIF/BMP/TIFF decode and encode support remains a follow-up.
- Slider uses native WinUI `Slider` with value/min/max/tick support, pointer press/release events, and focused Testbed coverage.
- DateInput uses native WinUI `DatePicker` with native min/max dates; TimeInput uses native WinUI `TimePicker` with minute-resolution values and backend-enforced min/max limits because the native control does not expose limit properties or seconds selection.

## Known Gaps

- Custom variable font face selection remains unsupported; registered TTF/OTF font files now load through XAML file URI `FontFamily` sources, and arbitrary system font names are validated against the Windows font registry.
- Image support is currently PNG-only for load/save/data roundtrips; JPEG, GIF, BMP, and TIFF support need either WinRT encoder/decoder coverage or a deliberately chosen dependency.
- TimeInput is minute-resolution because WinUI `TimePicker` does not expose seconds selection; min/max limits are enforced by the backend rather than native picker properties.
- Table cell icons and widgets are supported in all columns through native WinUI `Image` cells and hosted child controls.
- Tree uses native WinUI `ListView` rows with backend-managed expansion rather than the native WinUI `TreeView`, because Toga's Tree requires multi-column cells; Tree cell icons and widgets are supported in all columns through native WinUI `Image` cells and hosted child controls, structural insert/delete collapses expansion state, and structural insert/delete clears selection.
- DetailedList actions and refresh are currently exposed through backend/probe hooks, not native swipe, pull-to-refresh, or context-menu UI.
- Canvas uses native WinUI `CanvasControl` and a Win2D `CanvasRenderTarget` for `as_image()` export, drawing actions now render through Win2D for normal paint/export paths, and visual reference tests are enabled with WinUI-specific variants for stable raster differences; the remaining canvas xfails are the shared text-rendering tests that are unstable outside CI.
- MapView now uses XAML `WebView2` with Leaflet/OpenStreetMap instead of the prior backend-managed placeholder; remaining gaps are provider configurability, offline/runtime failure handling, geolocation, native Windows map-service integration if one becomes viable, and Testbed coverage that validates the actual rendered map surface rather than only Toga state/probe behavior.
- The backend currently implements and has focused Testbed coverage for 25 widget entry points: ActivityIndicator, Box, Button, Canvas, DateInput, DetailedList, Divider, ImageView, Label, MapView, MultilineTextInput, NumberInput, OptionContainer, PasswordInput, ProgressBar, ScrollContainer, Selection, Slider, SplitContainer, Switch, Table, TextInput, TimeInput, Tree, and WebView.
- The backend has no disabled widget entry points left in `winui3/pyproject.toml`; the latest focused scan of `winui3/pyproject.toml` and `winui3/src/toga_winui3/factory.py` confirmed every current widget entry point is enabled.
- WinUI app resource initialization still uses the proven absolute `ms-appx:///.../winui3app.xaml` `Application.LoadComponent()` locator in this unpackaged Python path; direct `XamlControlsResources()` activation and package-relative `ms-appx:///winui3app.xaml` were tested and rejected because they crash or terminate startup, but normal resource fallback probes are no longer printed during Testbed startup.
- Command shortcuts now have native WinUI menu `KeyboardAccelerator` objects, shortcut display text, key-conversion coverage, and focused physical `SendInput` coverage for enabled and disabled menu shortcut invocation; remaining shortcut hardening would be broader OS keyboard-layout and focus-stealing edge cases rather than the basic accelerator path.
- WinUI app-level hide/unhide remains xfailed and is explicitly treated as a native Windows platform limit: WinUI desktop apps do not expose the macOS-style global application Hide/Unhide menu model. Native WinUI window-management menu actions now pass through real menu items, document opening by drag is wired through XAML drop handling, startup document/file activation is covered, and WinUI still needs its own DPI-change coverage because the current Testbed DPI test is WinForms-specific.
- WinUI fullscreen/presentation tests are stable, but this is not true native fullscreen parity yet: the backend intentionally avoids `AppWindowPresenterKind.FullScreen` because the latest focused experiment failed Toga's window-size transition contract even though it did not reproduce the earlier native access violation, and it also avoids `OverlappedPresenter.SetBorderAndTitleBar(False, False)` because title-bar restoration changed the normal client size on plain windows.
- Widget behavior gaps intentionally recorded in probes: undo/redo are skipped globally by `winui3/tests_backend/widgets/base.py`; WebView content root URLs and JavaScript exceptions are marked unsupported to match Windows/WebView2 behavior.
- File/folder dialogs now use native Windows App SDK pickers in normal use, but the installed `win32more-Microsoft.WindowsAppSDK` binding does not expose custom picker `Title`, exact arbitrary `SuggestedFolder` support for open/folder pickers, or multiple folder picking; save dialogs only pass `SuggestedFolder` when the path exists because the native setter rejects invalid folders.
